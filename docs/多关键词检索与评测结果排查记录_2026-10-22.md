## 1. 本次问题

完成固定题集运行后，观察到三个现象：

1. 结果中的 method 显示“人工预设关键词检索并直接展示全文，无模型生成”，容易被理解为模型没有参与回答。
2. 参照结果明明包含资料文件，Agent 却达到请求上限。
3. 参照结果包含资料文件，Agent 却输出“未找到相关本地资料”。

本次先查看代码和原始执行记录，再区分报告字段、检索行为和模型生成质量，没有直接延长等待时间或放宽无来源保护。

### 2.1 method 是参照组说明，不是模型自述

每份评测结果同时包含两组数据：

| 字段 | 含义 |
| --- | --- |
| baseline.method | 人工预设关键词检索参照的方法 |
| baseline.sources | 人工预设关键词实际找到的文件 |
| baseline.answer | 检索到的资料正文，不经过模型生成 |
| agent.answer | Agent 最终返回的回答，可能被程序的无来源保护替换 |
| agent.sources | Agent 本次实际读取的文件 |
| debug | Agent 的模型响应、搜索参数和工具执行记录 |

baseline 由 evaluate.py 使用题集中的 keyword 和 language 独立生成，不会发给模型，也不能证明 Agent 自己找到了相同文件。

因此，baseline.method 保留“无模型生成”是正确的。阅读模型结果应查看 agent.answer、agent.sources 和 debug。本次已澄清字段含义；当前 evaluate.py 和 retry_v2 结果中尚未新增 agent.method，不能将此前提出的字段标注建议记录为已经落地。

| 题目 | agent.status | 总耗时 | 判断 |
| --- | --- | --- | --- |

### 2.3 真正的失败点：模型输出多词查询，工具按整段文字匹配

原 search_docs 的核心判断是：

    if keyword in line.lower():

它要求整段关键词连续出现在某一行，不会自动将空白分隔的词理解为独立搜索词。

修改前的典型工具参数：

| 题目 | Agent 实际关键词 | 实际工具来源 |
| --- | --- | --- |
| print | print sep end | 空列表 |
| dict | 字典按键取值 default value | 空列表 |
| c_pointer | 数组指针 多维数组 | 空列表 |
| c_pointer 后续请求 | int *a[] 二维数组指针 | 空列表 |

例如，资料里有 print、sep 和 end，也不等于某一行包含连续文本“print sep end”。

失败链路为：

    模型给出多个词组成的查询
        → 工具搜索整段连续文本
        → 没有匹配行
        → 没有文件全文回传模型
        → 模型重复搜索，或程序最终执行无来源拒答

因此，这批拒答不是“Agent 已读到文件却把来源丢了”。找到文件的是独立参照组，Agent 当时的实际搜索没有命中。

问题应归到工具对多词查询的兼容性，不能仅归因于提示词严格或模型解释能力。

## 3. 实际修改

修改位置：agent.py 的 execute_search 中，首次调用 search_docs 之后、收集 source_names 之前。

    matches = search_docs(key_word, language)
    terms = key_word.split()

    if not matches and len(terms) > 1:
        print("完整关键词未匹配，分别搜索：", terms)

        seen = set()

        for term in terms:
            term_matches = search_docs(term, language)

            for item in term_matches:
                identity = (item["source"], item["line_number"])

                if identity in seen:
                    continue

                seen.add(identity)
                matches.append(item)

新处理顺序：

1. 先使用完整关键词搜索。
2. 完整搜索为空，并且查询包含多个空白分隔的词时，启动回退。
3. 分别搜索每个词，继续使用原来的 language 参数筛选。
4. 合并各词的匹配结果；以“来源文件名、行号”组成的元组去重。
5. 交给已有逻辑按文件名去重、读取全文并回传模型。

两个具体例子：

    print sep end
        → 完整搜索为空
        → 分别搜索 print、sep、end
        → 合并匹配行并读取对应文件

    int *a[]
        → 完整搜索已命中
        → 不进入拆词回退
        → 保留包含空格的 C 语法整体匹配

该修改位于工具执行层，没有更改 search_docs 的函数签名、模型、系统提示、四轮上限或无来源保护。

## 5. 当前边界与本次停点

拆词回退采用“任一词匹配就合并”的方式，可以兼容多词查询，但不保证召回文件一定与完整问题相关。例如 print 同时命中字典示例和 print 专题，是当前文字包含匹配的实际行为。

对于未被空白分隔的同义表达，本次没有加入语义理解能力。即使读取了正确资料，模型仍可能解释错误；这与本次解决的“多词查询未命中”是不同问题。

本次确认完成的是：定位报告字段误读、区分轮次上限与网络超时、落地整段搜索失败后的拆词回退，并保存前后检索结果和现有回归证据。后续可以继续完成第五阶段的交付记录，不因这次修复自动扩展模型优化范围。
